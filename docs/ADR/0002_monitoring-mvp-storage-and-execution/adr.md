# ADR-0002: 모니터링 MVP 저장소와 실행

상태: 채택됨

날짜: 2026-08-01
수정일: 2026-09-12

## 배경

PRD-0003은 DB에 저장한 점검 일정, 리스, 불변 시도/결과 이력, 현재 점검 상태과 원자적
상태 변경 이벤트를 요구한다. 작업자는 적대적이거나 느린 네트워크 I/O를 수행하는
동안 데이터베이스 트랜잭션을 유지해서는 안 된다.

이 결정을 내릴 당시 저장소에는 영속성과 외부 어댑터 모듈이 있었지만 데이터베이스,
마이그레이션 도구, 저장소 API 또는 HTTP 클라이언트를 선택하지 않은 상태였다.

## 결정

MVP 데이터베이스로 PostgreSQL, 추가 전용 스키마 마이그레이션 도구로 Flyway,
명시적 SQL과 트랜잭션 경계를 위해 Spring JDBC를 사용한다. 영속성 어댑터는
다음 네 테이블을 관리한다.

- `watch_monitor`: 원본 리비전, 활성 일정, 리스와 현재 점검 정보
- `watch_attempt`: 불변 선점 스냅샷
- `watch_result`: 불변 완료 결과 메타데이터
- `watch_health_change_event`: 상태 변경 이벤트 아웃박스와 ADR-0003에서 확장한
  대기/전달 완료 상태, 전달 시도, 예정 시각, 만료되는 리스, 제한된 결과, 응답
  확인 시각과 보존 대상 여부

선점은 `SELECT ... FOR UPDATE SKIP LOCKED`를 사용하는 짧은 트랜잭션에서
수행한 뒤 리스 토큰을 갱신하고 시도를 삽입한다. 애플리케이션은 해당 트랜잭션이
반환된 뒤 점검을 수행한다. 확정 작업은 모니터를 잠그고 리스 토큰과 원본 리비전을
검증한 뒤 결과를 삽입하고, 도메인 정책으로 상태를 도출하고, 프로젝션을 갱신하며,
상태가 변경되었으면 한 트랜잭션에서 이벤트를 삽입한다. 시도 식별자는 고유하므로
확정을 반복해도 아무 작업도 하지 않는다.

리스 토큰은 모니터 행에만 두고, 확정은 잠근 모니터 행의 시도 ID·리스 토큰·원본
리비전으로 소유권을 대조한다. 무작위 리스 토큰에는 고유 인덱스를 두지 않는다.
시도 스냅샷의 `lease_expires_at`과 `lease_expires_at > claimed_at` CHECK는 리스
기간이 양수라는 DB 수준 검증으로 유지한다.

점검과 전달 선점은 데이터베이스 연결을 획득한 뒤 선점 트랜잭션의
PostgreSQL `transaction_timestamp()`를 읽어 리스 기준 시각으로 사용한다. 이로써
연결 풀 대기 시간이 리스 기간을 미리 소비하지 않고 다중 인스턴스의 시각
기준을 데이터베이스로 통일한다.

배치 전체를 미리 선점하지 않고 각 네트워크 호출 직전에 한 건씩 선점한다. 배치
크기는 예약 실행당 최대 처리 수로만 사용한다. 시작 검증은 리스에 선점·확정
트랜잭션 제한 두 번, 확정 연결 대기와 외부 전체 제한을 합산하고, 직렬 배치에는
선점·확정 연결 대기와 트랜잭션 제한 두 번 및 외부 전체 제한을 항목 수만큼
합산한다. 리스는 전자의 계산값을 초과해야 하며 배치는 60초 이하의
`workerExecutionBudget` 안에 들어야 한다. 기본 점검 배치는 1건, 전달 배치는
2건이다.

점검·전달 배치는 각 선점 전에 JDK `Thread.currentThread().isInterrupted()`로
인터럽트 상태를 확인하고, 중단 요청이 있으면 새 항목을 선점하지 않는다. 이미
선점한 항목의 외부 호출이 반환하면 기존 확정 경로를 수행하고 다음 반복을 끝낸다.
인터럽트 상태는 보존하며 별도 취소 상태 객체를 두지 않는다. 확정 실패는 기존
오류 전파와 리스 만료 복구를 따르고, 정상 종료 대기 설정은 변경하지 않는다.

어댑터가 소유한 모든 영속성 트랜잭션에는 Spring 트랜잭션 타임아웃 5초를
적용한다. PostgreSQL `lock_timeout` 1초는 WATCH 전용 Hikari 풀의 모든 연결에
pgJDBC `options` 시작 매개변수(`-c lock_timeout=<ms>ms`)로 적용한다. 잠금 제한은
더 넓은 구문 기한보다 먼저 잠금 경합을 실패시킨다. 풀의 모든 연결이 시작부터
같은 값을 가지므로 풀링된 연결이 이후 작업으로 다른 설정을 전달하지 않고,
트랜잭션마다 설정 왕복도 없다. 비트랜잭션 조회도 DDL 같은 테이블 잠금을 1초
넘게 기다리지 않고 `55P03`(API 503)으로 실패한다. 로컬 Compose와 테스트에서
앱이 같은 DataSource로 실행하는 Flyway도 같은 제한을 받으며, 바쁜 테이블 DDL이
필요해지면 `spring.flyway.init-sqls`로 완화할 수 있다. 트랜잭션 풀링 중계기는
`options`를 지원하지 않을 수 있으므로 도입할 때 이 결정을 다시 검토한다. 호출자가
이미 Spring 트랜잭션을 소유하고 있으면 영속성 작업은 시작 전에 실패하여
애플리케이션의 네트워크 I/O가 실수로 외부 트랜잭션 안에서 실행되지 않게 한다.

Boot의 공유 `JdbcTemplate`에는 쿼리 타임아웃 5초가 설정되어 있다. 자동 설정된
`JdbcClient`는 `NamedParameterJdbcTemplate`을 통해 해당 템플릿을 재사용하므로
WATCH가 별도 JDBC 래퍼를 소유하지 않아도 동일한 구문 기한이 비트랜잭션
프로젝션 조회와 이벤트 백로그 집계를 제한한다. 활성 Spring 트랜잭션은 남은
트랜잭션 시간에 맞춰 실효 구문 기한을 더 짧게 만들 수 있다.

같은 `JdbcTemplate`에 `SQLErrorCodeSQLExceptionTranslator("PostgreSQL")`을 적용한다.
기본 변환기가 미분류로 처리하던 잠금 시간 초과(`55P03`)를 Spring 표준의
`CannotAcquireLockException`으로 분류해 API의 503·재시도 안내에 연결한다.
Spring 내장 매핑을 사용하며 제품 이름을 명시해 설정 시 DB 메타데이터 연결을 추가하지 않는다.

`watch.persistence.query-timeout`과 `watch.persistence.transaction-timeout`은
1~30초의 정수 초 단위여야 한다. HikariCP에는 최대 풀 8, 최소 유휴 연결 2,
연결 대기 3초, 검증 1초, 유휴 10분, 최대 수명 30분, 생존 확인 2분,
초기화 실패 5초의 기본 한도를 둔다. 허용 범위는 최대 풀 1~32,
최소 유휴 0~32, 연결·검증 250~30000ms, 유휴 10000~1800000ms,
최대 수명 30000~3600000ms, 생존 확인 30000~1800000ms,
초기화 실패 1~30000ms다. 최소 유휴는 최대 풀 이하, 검증은 연결
대기보다 짧게 제한한다. 최소 유휴가 최대 풀보다 작은 가변 풀에서는 유휴 제한을
최대 수명보다 1000ms 이상 짧게 두며, 생존 확인은 최대 수명보다 짧게 제한한다.

pgJDBC에는 연결 3초, 로그인 5초, 소켓 10초, 취소 신호 3초,
TCP keepalive 기본 활성화와 `options`의 `lock_timeout`을 명시한다. 연결·로그인·취소 신호는
1~30초, 소켓은 1~120초, TCP keepalive는 불리언만 허용한다. 이 값들은
`WATCH_PERSISTENCE_QUERY_TIMEOUT`과 `WATCH_DB_*` 환경 변수로 재정의하되,
연결 풀과 데이터베이스 서버 한계의 합을 같이 검토해야 한다.
검증된 WATCH 설정이 실제 HikariCP와 pgJDBC 속성을 직접 구성한다. JDBC URL은
`jdbc:postgresql://` 계층형 형식이어야 하며, 드라이버 속성 상한을 우회할 수 있는
URL 쿼리 매개변수는 허용하지 않으므로 `options` 우회도 막는다. 테스트 서비스 연결의 비식별 로깅 비활성화
값인 `loggerLevel=OFF`만 예외로 허용한다.

외부 어댑터에서 Apache HttpClient 5를 사용한다. 자동 리다이렉트는 비활성화한다.
각 경유 단계마다 정책 컴포넌트가 원래 호스트를 파싱하고 해석하여 비전역 주소를
거부하고, 요청 범위 클라이언트 DNS 해석기에 승인된 주소만 제공한다. 요청 URI는
원래 호스트를 유지하므로 HTTP Host, SNI와 TLS 호스트 이름 검증이 올바르게
동작한다. 애플리케이션은 아웃바운드 점검기 포트에만 의존한다. 대상 GET은 각 홉의
상태·헤더를 읽고 `CloseMode.IMMEDIATE`로 응답을 닫는다. 성공 경로에서도 본문을
소비하거나 비우지 않아 큰 HTML·파일·스트리밍 본문이 거짓 장애 판정이나 작업자
점유를 유발하지 않게 한다. HEAD로 바꾸지 않으므로 메서드별 서버 지원 차이를
추가하지 않는다. 본문 전체 전송 성공은 점검 범위가 아니다.

대상 점검과 콜백 전달은 `ApacheHttpRequestExecutor.executePinned` 하나로 요청을 실행한다.
이 메서드가 요청마다 IP 고정 클라이언트를 열고, 응답 헤더를 받은 시점을 기록하며, 성공 시 닫기 방식을
호출자에게서 받는다. 대상 점검은 즉시 닫고 콜백 전달은 제한된 본문 소비 후 정상 종료하며, 두 경로 모두 실패 시 즉시
종료한다. 대상 점검에는 응답 바이트 설정과 기록을 두지 않는다. 헤더·시간·목적지·큐
상한과 콜백 전달의 바이트 제한은 유지한다.

DNS 조회와 HTTP 요청은 공용 제한 실행기 `BoundedTaskExecutor`에서 실행한다. HTTP 요청은
실행기에 제출하기 전에 만든다. 이미 인터럽트된 호출은 제출하지 않고, JDK `FutureTask.done()`의
취소 분기에서 취소 훅을 호출한 뒤 JDK `ThreadPoolExecutor.remove()`로 대기열에서 작업을 뺀다.
HTTP의 취소 훅은 Apache `HttpUriRequestBase.cancel()`이다. 플랫폼 스레드의 인터럽트만으로는
소켓 읽기가 끝나지 않을 수 있으므로 시간 초과와 호출자 중단을 실제 연결 취소에 연결한다.
취소한 대기 작업의 자리는 바로 비워지므로 실행 중인 작업이 지연돼도 새 요청이 대기열을 사용할 수 있다.
실행기는 완료되지 않은 작업만 추적하며, 종료 시 새 제출을 차단하고 실행 중인 작업과 대기 작업을
모두 취소한 뒤 작업자를 인터럽트한다. 대기·실행 중인 작업의 호출자는 남은 기한을 기다리지 않고
반환하며, 제출 거부·호출자 중단·종료 취소는 `INTERNAL_FAILURE`로 바꿔 대상의 DNS 장애와 구분한다.
실행 중인 JVM 리졸버를 강제로 멈추는 구현, 별도 감시·정리 스레드나 소켓 관리 구현은 두지 않으며
기존 스레드 수와 대기열 상한을 유지한다.

고정 리졸버가 해석할 호스트는 Host·SNI와 같은 Apache 요청 authority에서 정한다.
리졸버는 승인된 주소만 반환하며 DNS를 다시 조회하지 않는다.

Bootstrap은 Apache HttpClient의 원본 헤더, wire, 구현과 TLS 로거 범주 및
Spring JDBC의 `StatementCreatorUtils` 구문 매개변수 로거를 `OFF`로 고정한다.
외부 설정보다 우선하는 Spring Boot 환경 후처리기 속성
소스가 이 값을 적용한다. 더 구체적인 이 레벨은 루트 또는 더 넓은 Apache HTTP 패키지가
`DEBUG`로 올라가도 유효하므로 Bearer 헤더, 대상 쿼리, 페이로드, 응답 본문,
호스트 이름, 해석된 주소, 인증서 이름과 원본 닫기 실패 예외가 WATCH의 비식별화된
애플리케이션 로그를 우회하지 못하게 한다. 운영자는 보호되는 이 하위 범주를
명시적으로 재정의해서는 안 된다.

`TargetUrl`은 생성할 때 원문 문자, 퍼센트 인코딩된 제어 문자·DEL·역슬래시와 URI 구조를
모두 검사하며, 스냅샷 수락, 저장 행 재구성과 각 리다이렉트 재검증에 같은 규칙을 적용한다.
대상 URL은 이 검사를 통과한 동기화 값만 저장하므로 점유 때 다시 만들어도 실패하지 않는다.
규칙을 강화할 때는 같은 변경에서 Flyway로 위반 행을 정리한다. 외부 어댑터는 DNS/주소 승인 전에
원본 리다이렉트 참조 검증, 해석과 루프 감지를 위한 정규화만 추가한다.

쿼리만 지정한 리다이렉트는 현재 URI의 원문 경로에 참조를 그대로 붙여 해석한다.
JDK `URI.resolve`는 `/docs/page?old=1`과 `?page=2`를 `/docs/?page=2`로 합치고,
Apache `URIUtils.resolve`는 `/문서` 같은 비ASCII 경로를 퍼센트 인코딩해 순환 판정 키가
달라지므로 둘 다 쓰지 않는다. 해석 전 문자 검사, 해석 후 대상 검증,
DNS 재검증·IP 고정·순환 감지와 리다이렉트 상한은 그대로 적용한다.

Spring 예약 기능은 bootstrap에 있으며 애플리케이션 유스케이스를 호출한다. 대상
점검, 콜백 전달과 데이터베이스 유지보수는 서로 독립된 이름 있는 단일 스레드
스케줄러를 사용한다. 프로세스당 점검 배치와 전달 배치를 각각 하나씩 실행하며,
느린 콜백이 대상 점검이나 유지보수를 굶기지 못한다. 예상하지 못한 실패는 예약
메서드 밖으로 전파되어 Spring 내장 `tasks.scheduled.execution` 관측이 오류를
기록하게 한다. Spring Boot 예약 작업 관측 자동 구성은 사용 가능한
`ObservationRegistry`를 Spring 예약 작업 등록기에 연결한다. 이후 공유
비식별화 스케줄러 오류 처리기는 예외 클래스만 기록하고 실패를 억제하여 주기
작업이 계속 예약되도록 한다. 오래된 프로젝션 표시, 시도 이력 보존, 전달 완료
이벤트 정리, 점검 지연과 전달 백로그 갱신은 동일한 단일 스레드 유지보수 실행로의
서로 다른 메서드다. 이를 통해 각 작업의 독립성을 유지하고 WATCH 자체 스케줄러 실패
카운터 없이 제한된 프레임워크 메서드 식별자를 부여한다.

`MonitoringScheduler`에는 점검 예약만 두고 Spring `Condition`에서
`Environment.getProperty`의 `Boolean` 변환으로 `watch.check-enabled`를 읽는다.
Spring 불리언 표현을 허용하고 해석할 수 없는 값은 시작에 실패한다. 사용자 설정 빈을
조건 평가 중 미리 초기화하지 않는다. 누락 시 기본은 활성이며 별도 플래그 감시 스레드나 동적 제어 API를 만들지 않는다.
`MonitoringMaintenanceScheduler`는 오래된 상태·시도 보존·시계 편차 측정과
점검 지연 갱신을 담당해 점검 비활성 상태에서도 등록된다. 기존 전달 및 전달
유지보수 등록 조건은 유지한다.
이 설정은 인스턴스 시작 시 적용하며 DB에 있는 모니터 상태와 일정을 변경하지 않는다.

실제 대상 점검은 제한된 `outcome` 차원만 사용하는
`baton.watch.check.attempts`와 `baton.watch.check.duration`에 기록하며,
기록은 Micrometer 기본 동작에 맡긴다. 기록 예외가 점검 결과·전달 확인·재시도를
바꾸지 않도록 예외를 던지는 `MeterFilter`, 등록 실패 시 예외를 던지는 리스너,
`baton.watch` 타이머의 `minimum-expected-value`·`maximum-expected-value` 설정을
쓰지 않는다. 점검기와 전달기 계측 데코레이터는 결과와 예외를 변경하지 않고 메트릭만
기록하며, 예기치 않은 실패를 `INTERNAL_FAILURE`로 바꾸는 책임은 애플리케이션
서비스에 둔다. `baton.watch.check.inflight` 게이지는 실제 점검 호출 전후에
증가·감소하며 식별자 레이블을 사용하지 않는다. `baton.watch.check.schedule.delay`
게이지는 유지보수 주기마다 선점 조건과 같은 상태·예정 시각·리스 조건으로 지금
실행 가능한 점검 중 가장 오래 지연된 한 건을 읽고 PostgreSQL 시각과의 차이로 갱신한다.
기존 `watch_monitor(next_check_at, resource_reference)` 부분 인덱스와
`ORDER BY ... LIMIT 1`을 사용하며 전체 적체 건수 집계, 새 테이블과 식별자
차원을 추가하지 않는다. 선점 가능한 점검이 없으면 0으로 갱신한다.
점유와 완료 처리는 영속성 포트 데코레이터에서 항목별로 기록하여 뒤 항목의
저장 실패가 앞서 처리한 항목의 기록을 지우지 않게 한다. 점검과 전달은 각각 점유,
제한된 완료 상태와 만료 리스 회수 카운터를 사용한다. 유지보수 작업은
PostgreSQL `clock_timestamp()`와 JDBC 왕복 전후 JVM 시각의 중간점을 비교한
부호 있는 시계 편차 게이지를 갱신한다.

Spring은 내부 예약 작업 진단을 위해 원래 작업 예외를 유지하므로 Actuator
`scheduledtasks` 엔드포인트는 공개 관리 허용 목록에서 제외한다. `health`와
`prometheus`만 공개한다. 같은 환경 후처리기 속성 소스가 상세 상태 비공개와
관리 허용 목록뿐 아니라 관리 서버 주소 `127.0.0.1`도 고정하여 실행 방식이나
외부 설정이 관리 경로의 노출 범위를 넓히지 못하게 한다.

Compose의 WATCH 상태 확인은 Spring Boot 기본 readiness 그룹을 사용하며
`readinessState,db`만 포함한다. liveness에는 DB를 포함하지 않는다. 별도 상태
확인 컨트롤러나 DB 조회 구현을 만들지 않고, 관리 포트 비공개를 유지한다.
Docker의 unhealthy 상태만으로 자동 재시작이나 실행 중 트래픽 차단이 이루어지는
것은 아니다. 시작 의존성 확인과 운영 진단에 사용하는 상태 신호로 취급한다.

운영 화면은 기존 메트릭을 조회하는 Grafana JSON 템플릿으로 제공한다.
인스턴스별 DB 적체를 합산하지 않고 수집 누락은 빈 데이터로 남긴다. 평균 HTTP
시간은 기존 타이머의 합계/횟수로 계산하며 히스토그램이나 점검 적체 전체 집계를
도입하지 않는다.

운영자의 개별 장애 분석은 별도 HTTP API 대신 PostgreSQL `psql` 기반 읽기 전용
CLI로 제공한다. 기존 리소스별 인덱스와 한 SELECT의 스냅샷으로 현재 상태 및 최근
점검·전달 이력을 조회한다. 각 이력은 최대 100건이며 URL·호스트·리스 토큰은
선택하지 않는다. 읽기 전용 트랜잭션, SQL·잠금·트랜잭션 시간 제한은 PostgreSQL
기능을 사용한다. 스키마·런타임 의존성·DB 쓰기 권한은 추가하지 않는다.
`psql`의 `\bind`로 조회 값을 SQL 본문과 분리하고, 진단 트랜잭션에서
`log_parameter_max_length`와 `log_parameter_max_length_on_error`를 `0`으로
설정한다. 따라서 기본 오류 로그와 상세 SQL 로그를 유지하면서 리소스 참조를
제외한다. 로그 보호 설정 권한이 없으면 조회 전에 실패하며 권한을 자동 부여하지 않는다.

Prometheus 조회 경로만 유지하고 관리 서버는 컨테이너 루프백에 바인딩한다.
WATCH가 외부 모니터링 서비스로 메트릭을 직접 전송하는 기능은 제공하지 않는다. 외부
메트릭 전송을 다시 도입하려면 공개 IP 검증, 검증한 IP에 연결 고정,
리다이렉트 금지, 시간·헤더·응답 바이트 상한과 비식별 로그를 포함한 같은
외부 통신 보안 조건을 충족하고 별도 ADR로 채택해야 한다. 현재 결정은 외부 계정,
대시보드 또는 알림이 실제 준비되었다는 의미가 아니며 유료 저장소나 유료 엣지
기능을 채택하지 않는다.

배치 크기, 리스, 간격, 타임아웃, 바이트 제한, 결과 만료 기준, 보존 기간과 정리 배치
크기는 제한된 설정값이다. 보안과 메모리 할당에 민감한 바이트, 헤더, 실행기, 큐와
배치 설정에는 런타임 설정이 넘을 수 없는 불변 구현 상한도 적용한다.
점검·전달 폴링은 최소 1초, 유지보수는 최소 60초, 일반 점검은 최소 60초,
내부 실패 재시도는 최소 30초, 이벤트 전달 재시도 지연은 최소 5초다.
시각에 더하거나 빼는 양의 설정 기간은 설정 바인딩의 `@DurationMax(days = 365)`로
제한한다. 이벤트 전달 설정 바인딩은 재시도 지연의 5초 최소값만 검증하고,
`EventDeliveryRetryPolicy`가 초기 지연과 최대 지연의 순서 및 30일 상한을
검증한다.

Bootstrap 바인딩은 민감하지 않고 서로 독립적인 숫자와 양의 기간 제한, 중첩 속성
존재 검증을 Spring Boot 설정 속성 Bean Validation에 위임한다. 비밀값 구문과
`staleAfter`·점검 간격, 작업자 실행 예산 같은 필드 간 비교는 거부된 값을 드러내지 않도록
직접 검사한다. 실행 예산 계산의 오버플로는 먼저 만들어지는 외부 제한 객체가 나노초 표현
범위를 검증해 막는다. 외부 어댑터는 bootstrap 검증에서 설정을 이미
수락했더라도 리소스 경계에서 메모리 할당 상한을 계속 적용한다.

내장 Tomcat은 요청·응답 헤더를 각각 8 KiB, 연결을 128개, 수락 대기를 32개,
워커 스레드를 최대 32개·최소 유휴 4개, 워커 큐를 64개로 고정한다. 검증된
인바운드 자원 상한을 런타임 설정으로 우회하지 못하도록 외부 설정보다 우선하는
Spring Boot 환경 후처리기 속성 소스가 이 값을 적용한다. 같은 소스는 Spring 종료
단계별 제한 30초와 예약 작업 종료 대기 65초도 고정해 컨테이너 종료 대기 110초 안에
들어오게 한다. 이 상한은 단일 오리진 자원을 제한하지만 공개 엣지의 요청
속도 제한을 대신하지 않는다.

내부 모니터 API는 런타임에 공급되는 하나의 Bearer 토큰을 사용하며, 이 토큰에는
RFC 6750 `token68`의 패딩이 아닌 문자가 32자 이상 있어야 하고 전체 길이는
200자 이하여야 한다. 시작 시 설정이
검증된 후에는 Spring Security의 표준 Bearer 해석기가 헤더 파싱을 담당한다. 이는
서비스 인증일 뿐이며 WATCH는 여전히 BATON의 인가 결정을 내리지 않는다.

## 결과

SQL은 PostgreSQL에 종속되며 영속성 통합 테스트는 PostgreSQL, 특히 리스 경쟁,
복구, 오래된 리비전과 마이그레이션을 실행해야 한다. Spring JDBC를 사용하면 수동
매핑이 필요하지만 잠금과 트랜잭션 범위를 명확하게 드러낼 수 있다.

트랜잭션 제한은 트랜잭션 범위 JDBC 구문과 행 잠금 대기에 적용되며, 공유 Spring
JDBC 쿼리 타임아웃도 비트랜잭션 프로젝션과 백로그 구문을 제한한다. 연결 시작
매개변수의 `lock_timeout`은 비트랜잭션 조회와 앱이 실행하는 Flyway 연결에도
적용된다. 이 구문 기한은
연결 획득이나 JDBC 취소를 완료할 수 없는 네트워크 경로를 제한하지 못한다. 해당
경로에는 데이터소스와 런타임 제어가 계속 필요하다. 독립된 스케줄러 실행로는 최대
세 개의 데이터베이스 연결을 동시에 사용할 수 있으므로 풀 크기에는 최소한 그만큼의
운영 여유를 남겨야 한다.

DNS 고정에는 해석기를 주입할 수 있는 HTTP 클라이언트가 필요하다. Java 21은
이에 상응하는 요청별 해석기를 제공하지 않으므로 JDK HTTP 클라이언트를 사용하지
않는다. 리다이렉트 처리와 응답 소비는 명시적이며 테스트 가능하게 유지한다. JVM
해석기 자체는 강제로 취소할 수 없으므로 제한된 해석기 실행기와 인프라 송신 정책은
심층 방어로 계속 필요하다.

이벤트 테이블에는 상태 갱신과 같은 트랜잭션에서 이벤트를 저장한다. PRD-0004와
ADR-0003에서 채택한 HTTPS 디스패처가 저장된 이벤트를 읽어 전달한다. 전달은 네트워크 I/O 전후에 별도의 짧은 선점 및
확정 트랜잭션, 상한이 적용된 지수 재시도와 확인된 이벤트만 삭제하는 보존 정책을
사용한다. 브로커는 채택하지 않는다.

운영 데이터가 생기기 전인 2026-10-05에 V1~V6을 최종 스키마를 바로 만드는 단일 V1로 통합했다.
기존 데이터 이행 구문과 이행 경로 시험은 제거했다. 2026-10-07에도 운영 데이터가 없어 V1을 직접 고쳐
백로그 요약 테이블·트리거·함수, `watch_monitor.created_at`·`updated_at`, `watch_attempt.lease_token`,
리스 토큰 고유 인덱스, `PENDING` `changed_at` 인덱스를 지웠다. 이전 V1을 적용한 DB는 Flyway 체크섬
검증에 실패하므로 볼륨을 지우고 다시 만든다. 운영·스테이징 데이터를 보존해야 하는 시점부터는 적용된
마이그레이션을 고치지 않고 새 버전 파일로 추가한다.

전달 백로그는 별도 요약 행이나 트리거 없이 `PENDING` 부분 due 인덱스로 미전달
개수와 최소 `changed_at`을 한 구문에서 집계한다. 조회 비용은 미전달 건수에
비례하지만 유지보수 주기에만 실행하고 공유 쿼리 타임아웃의 제한을 받는다. 이벤트
쓰기는 요약 행 하나의 잠금으로 직렬화되지 않는다. 시도/결과 및 전달 완료
이벤트 정리는 정렬된 유한 후보를 `FOR UPDATE SKIP LOCKED`로 점유한 뒤
삭제하여, 제한 없는 삭제와 잠금 대기가 주기 작업을 가로막지 않게 한다.

전달 due 인덱스는 전달 선점 쿼리의 정렬 순서와 같은
`(next_attempt_at, changed_at, event_id)` 부분 인덱스를 사용한다. 리스가 참조하는
시도를 보존 후보에서 제외하는 조회를 위해
`watch_monitor(lease_attempt_id) WHERE lease_attempt_id IS NOT NULL` 부분
인덱스를 둔다. 전달 만료 리스 판정에 필요한
`delivery_lease_expires_at`은 due 인덱스의 포함 열로 유지한다.

스테이징에서는 PostgreSQL 소유자 역할과 WATCH 런타임 역할을 분리한다.
일회성 `database-role-init`가 런타임 역할을 설정하고, 소유자 자격 증명이
포함된 SHA 태그 `baton-watch-migrations:<full-git-sha>` 이미지만 Flyway를
실행한다. WATCH는
`SPRING_FLYWAY_ENABLED=false`로 시작하고 런타임 자격 증명만 받으며,
`flyway_schema_history`를 읽거나 변경할 수 없고 `public` 함수를 실행할 수도
없다. `PUBLIC`과 런타임 역할의 데이터베이스 `TEMPORARY` 권한도 심층 방어로
회수한다. 런타임은 모니터 테이블에 필요한 조회·삽입·갱신,
시도 테이블의 조회·삽입·보존 삭제, 결과 테이블의 조회·삽입, 이벤트 테이블의
조회·삽입·보존 삭제와 지정된 전달 메타데이터 열 갱신만 허용받는다. 불변 시도·결과 열과
이벤트 페이로드 열의 직접 갱신은 허용하지 않는다. 로컬 Compose의 단일 데이터베이스 역할
구성은 개발 편의용이며 스테이징 계정·권한 분리를 검증하는 용도가 아니다.

## 수동 재점검 예약

`watch_monitor.last_check_requested_at`은 마지막 수동 예약 접수 시각을 담는 nullable 열이다.
런타임 역할은 기존 모니터 UPDATE 권한을 사용하고 별도 테이블·인덱스·큐는 두지 않는다.

재점검은 동기화·선점·확정과 같은 모니터 행 잠금을 사용한다. 유효 리스나 도래한
일정은 그대로 사용하고, 새 예약은 일정과 접수 시각만 원자적으로 갱신한다. 30초
간격도 같은 잠금 안에서 판단하므로 동시 요청이나 인스턴스별 메모리 초기화로
우회하지 못한다. HTTP 202는 예약 접수만 의미하며 실제 외부 요청은 기존 작업자가 수행한다.

## 점검 진행 상태 조회

모니터 PUT·GET의 `checkStatus`는 기존 `next_check_at`·`lease_expires_at`과 주입된 `Clock`으로
계산한다. 상태를 따로 저장하면 시간 경과만으로도 갱신해야 하므로 새 열이나 작업자를 추가하지 않는다.
영속성 어댑터는 기존 조회의 리스 만료 시각을 내부 프로젝션에 담고, 도메인이 진행 상태를 판단한다.
웹 응답 DTO는 계산한 상태만 내보내며 리스 정보는 제외한다. 응답은 조회한 DB 값 기준의 상태이며
작업자 생존을 보장하지 않는다. 리스 점유·만료 복구·점검 완료 규칙은 유지한다.

## 여러 대상의 현재 상태 조회

자료별 HTTP 요청을 줄이기 위해 최대 20개의 식별자를 받는 GET을 추가한다. Spring MVC의
입력 변환·검증을 사용하고 `JdbcClient`의 바인딩된 `IN` 조회로 한 번에 읽는다. 기존 리소스
기본 키와 행 매핑을 재사용하며 별도 인덱스·테이블·캐시는 추가하지 않는다. 단건 GET도 같은
조회 경로에 식별자 하나를 넘긴다.

웹 응답은 요청 순서대로 중복을 제거하고 등록된 대상과 미등록 대상을 구분한다. 진행 상태는
응답 생성 시각 하나로 계산한다. 기존 단건 DTO를 재사용해 내부 리스 정보의 노출을 막는다.
식별자 20개의 입력은 기존 8 KiB 요청 헤더 한도 안에서 검증했다. 전체 목록을 열거하지 않고
명시한 대상만 반환하므로 커서 페이지네이션은 사용하지 않는다.
