# PRD-0003: URL 모니터링 MVP

상태: 채택됨

날짜: 2026-08-01
수정일: 2026-09-05

구현 상태: 완료; 이벤트 전달은 PRD-0004에서 별도로 구현됨

## 목표

이 MVP는 하나의 운영 흐름을 완성한다. BATON은 자체 트랜잭션을 커밋한 뒤
RoleResource의 URL 스냅샷을 동기화하고, WATCH는 이를 비동기식으로 검사하며,
BATON은 대상 네트워크를 기다리지 않고 최신 도출 상태를 조회할 수 있다.

이 계약으로 WATCH가 RoleResource 내용이나 인가의 권위 있는 원본이 되지는 않는다.

## 모니터 동기화

- 모니터는 BATON이 제공하고 WATCH가 의미를 해석하지 않는 `resourceReference`로 식별한다.
- 모든 동기화에는 BATON이 소유하는 음이 아닌 단조 증가 `sourceRevision`이 포함된다.
- 더 높은 리비전은 현재 스냅샷을 교체한다. 더 낮은 리비전은 오래된 것으로
  거부한다. 동일한 리비전을 동일한 페이로드로 반복하면 멱등성을 보장하며,
  이를 다른 페이로드에 재사용하면 충돌이다.
- `ACTIVE`에는 대상 URL이 필요하다. 새 모니터나 대상이 변경된 모니터는
  `UNKNOWN`으로 시작하며 즉시 검사 대상이 된다.
- `INACTIVE`에는 대상 URL이 없고 향후 검사를 중단하며 모든 리스를 무효화하지만
  제한된 이력은 보존한다. 더 높은 리비전의 `ACTIVE` 동기화로 다시 활성화할 수 있다.
- 현재 프로젝션은 대상 URL, 응답 본문, 조회된 주소 또는 내부 예외 내용을
  절대로 노출하지 않는다.

모니터 경로는 런타임 구성을 통해 제공된 고정 Bearer 토큰을 사용한다. 시스템
상태 경로는 계속 인증 없이 접근할 수 있다. 토큰 교체, 워크스페이스별 인가 및
최종 사용자 접근은 이 MVP의 범위에 포함되지 않는다.

## 일정 및 실행

- `watch.check-enabled`(`WATCH_CHECK_ENABLED`)는 기본 `true`다. 시작 시 `false`이면
  해당 인스턴스의 점검 예약을 등록하지 않는다. 전체 점검 활성 설정의 실시간 변경 API는 제공하지 않으며
  설정 변경은 프로세스 재시작 또는 컨테이너 재생성 후 적용한다.
  Spring 불리언 변환을 사용해 설정 바인딩과 예약 등록을 일치시키며, 불리언으로
  해석할 수 없는 값은 점검을 조용히 중지하는 대신 시작에 실패한다.
- 점검 중지는 모니터의 활성 상태·리비전·일정·리스를 초기화하지 않는다. API,
  오래된 프로젝션 처리, 이력 정리, 시계 편차 측정과 별도로 활성화한 이벤트 전달은
  유지한다. 설정 검증도 유지하며 전체 점검 중지는 모든 실행 인스턴스에 적용해야 한다.
- 중지 중 확정 결과가 오래되면 기존 규칙에 따라 `UNKNOWN`으로 바뀌고 이벤트가
  기록될 수 있다. 재개 후에는 기존 일정·리스·배치 상한으로 처리한다.
- 일반 검사 간격은 전체 런타임에 적용되는 기간이며 초기값과 최소값은 60초다.
- 점검 폴링 주기는 최소 1초, 유지보수 주기는 최소 60초이며 내부 실패 재시도
  주기는 최소 30초다. 더 짧은 설정은 작업을 시작하기 전에 거부한다.
- 새 활성 모니터와 변경된 활성 모니터는 즉시 검사 대상이 된다.
- 워커는 30초 리스를 사용하여 각 외부 점검 직전에 짧은 트랜잭션 안에서 처리
  시점이 된 모니터를 한 건씩 선점한다. 구성된 배치 크기는 한 번의 예약 실행에서
  처리할 최대 항목 수다.
- 리스 기준 시각은 데이터베이스 연결을 획득한 뒤 같은 선점
  트랜잭션의 PostgreSQL `transaction_timestamp()`에서 가져온다. 풀 대기
  시간이 리스 유효 기간을 미리 소비하지 않는다.
- 선점 시점의 소스 리비전과 대상을 담은 불변 시도 스냅샷을 생성한 뒤 DNS 또는
  HTTP 작업을 시작하기 전에 커밋한다.
- 확정은 별도의 짧은 트랜잭션에서 수행하며 시도 식별자를 기준으로 멱등성을 보장한다.
- 배치는 첫 선점과 다음 선점 전에 작업자 스레드의 인터럽트 상태를 확인한다.
  인터럽트 상태이면 새 항목을 선점하지 않고 반환한다. 이미 선점한 항목은 점검이
  반환하면 기존 확정 처리를 시도하며 인터럽트 상태를 지우지 않는다. 확정 실패 시
  기존 리스 만료 복구를 따른다.
- 만료된 리스는 다른 워커가 처리할 수 있다. 오래된 워커는 이후의 선점이나 소스
  리비전이 자신의 리스를 교체한 뒤 현재 상태를 갱신할 수 없다.
- MVP 실행은 의도적으로 프로세스당 한 번에 하나의 검사만 수행한다. 데이터베이스
  잠금과 리스를 사용하므로 여러 프로세스도 서로 겹치지 않는 작업을 선점할 수 있다.
- 시작 시 필요한 리스 기간과 전체 직렬 배치의 최대 실행 시간을 데이터베이스 연결·
  트랜잭션 제한과 외부 전체 제한으로 계산한다. 리스는 한 항목의 선점 이후 최악
  실행 시간을 넘어야 하고, 배치는 기본 60초이며 최대 60초인 허용 실행 시간 안에
  들어와야 한다.
- 10분 동안 확정적인 결과가 없는 모니터는 제한된 백그라운드 순회 작업에서
  `UNKNOWN`이 된다.
- 예약, 리스, 오래됨, 보존과 재시도 계산에서 `Instant`에 더하거나 빼는
  양의 설정 기간은 각각 365일을 초과할 수 없으며, 시각 범위를 넘는
  산술은 네트워크나 저장소 작업 전에 거부한다. 이벤트 전달 재시도는
  PRD-0004의 더 엄격한 30일 상한을 추가로 적용한다.

## 수동 재점검 예약

- 인증된 `POST /api/v1/resource-monitors/{resourceReference}/check-requests`는 기존
  활성 모니터의 다음 점검을 앞당긴다. 접수 응답은 HTTP 202이며 네트워크를 기다리지 않는다.
- 같은 모니터 행을 짧은 트랜잭션에서 잠근다. 실행 중인 유효 리스가 있으면
  `IN_PROGRESS`, 이미 점검 시각이 도래했으면 `ALREADY_SCHEDULED`로 합류한다.
  새 시도나 중복 일정을 만들지 않고 리스도 취소하지 않는다.
- 그 밖에는 `next_check_at`을 요청 시각으로 앞당기고 `last_check_requested_at`에
  접수 시각을 기록해 `SCHEDULED`를 반환한다. 원본 리비전·대상·상태·실패 횟수와
  최근 점검 결과는 보존하며, 접수 자체는 상태 변경 이벤트를 만들지 않는다.
- 새 수동 예약의 최소 간격은 리소스별 30초다. 기존 작업에 합류하는 요청은 허용하며,
  완료 뒤 다시 일정을 앞당기는 요청은 간격이 지나기 전까지 HTTP 429와 남은 시간을
  올림한 정수 초 `Retry-After`로 거부한다. 간격 판정은 DB 행에 보존되어 재시작과
  다중 인스턴스에서 공유되고 원본 재동기화로 초기화되지 않는다.
- 없는 모니터는 404, 비활성 모니터는 409다. 점검 예약이 꺼진 인스턴스도 접수는
  가능하지만 실제 실행에는 점검이 활성화된 작업자가 필요하다. 202는 실행·완료 보장이 아니다.
- 애플리케이션은 주입된 `Clock`으로 요청 시각을 정한다. 실제 점검과 완료 처리는
  기존 선점·네트워크·확정 경로와 안전 상한을 사용한다. 정확한 HTTP 계약은 PRD-0002를 따른다.

## 대상 및 요청 정책

- 절대 `http` 및 `https` URL만 허용한다.
- 각각의 기본 포트인 80과 443만 허용한다.
- URL 사용자 정보, 프래그먼트, IP 리터럴 호스트, 모호한 권한부, 제어 문자 및
  백슬래시는 거부한다. 쿼리 문자열은 검사할 수 있지만 로그에 기록하거나 API로
  노출해서는 안 된다.
- 동기화와 모든 리디렉션은 퍼센트 인코딩된 ASCII 제어 옥텟, DEL 및 백슬래시
  거부를 포함하는 동일한 정적 대상 구문 정책을 사용한다. 리디렉션 참조는 URI
  해석 전에 검사하고 해석 후 절대 대상으로 다시 검사한다.
- WATCH는 연결할 때마다 DNS 호스트 이름을 조회하고, 주소가 하나라도 전역 주소가
  아니면 DNS 조회 결과 전체를 거부한다. HTTP 및 TLS 검증을 위해 원래 호스트는 유지하면서
  승인된 조회 결과에 연결을 고정한다.
- 주소 정책은 클라우드 플랫폼 내부 서비스와 호스트 에이전트에 도달하는
  경로를 공개 IPv4처럼 보지 않는다. 특히 Azure WireServer
  `168.63.129.16/32`는 DNS 결과에 포함되면 연결 전에 명시적으로 거부한다.
- 저장소의 월간 작업은 주소 정책의 기준이 된 공식 IANA IPv4·IPv6 레지스트리
  체크섬을 비교한다. 원본이 바뀌면 자동으로 허용 범위를 넓히지 않고 작업을
  실패시켜 주소 정책과 경계 테스트의 수동 검토를 요구한다.
- 리디렉션은 명시적으로 처리한다. 모든 대상을 다시 검증하고 HTTPS에서 HTTP로의
  하향 이동과 리디렉션 순환을 거부하며 리디렉션 연결은 세 번으로 제한한다.
- 자동 재시도, 쿠키, 인증 캐싱, 프록시 탐색 및 응답 압축 해제는 비활성화한다.
- GET의 최종 응답 상태와 헤더로 도달 여부를 판단한다. 각 홉의 헤더를 받은 뒤
  본문을 읽거나 연결 재사용을 위해 비우지 않고 즉시 연결을 닫는다. 리다이렉트도
  본문 소비 없이 기존 목적지 재검증을 거친다. HEAD 지원 여부에 의존하지 않는다.
- 큰 `Content-Length`나 끝나지 않는 본문만으로 점검을 실패시키지 않는다.
  본문을 끝까지 내려받을 수 있는지, 로그인 뒤 실제 콘텐츠가 보이는지는 검증하지 않는다.
- 연결·응답·전체 시간, 헤더·실행기·큐 상한은 유지하며 헤더 제한 위반은 계속
  `RESPONSE_TOO_LARGE`로 분류한다. 실제 점검의 `responseBytes`는 0이다. 이는
  애플리케이션이 본문을 읽지 않았다는 뜻이며 소켓 버퍼에 받은 네트워크 바이트가
  0이라는 뜻은 아니다. 응답 본문은 영속화하지 않는다.
- 기존 `watch.http.max-response-bytes` 설정과 상한 검증은 구성 호환성을 위해
  유지한다. 본문을 읽지 않는 실제 점검의 성패에는 영향을 주지 않는다.
  PRD-0004 콜백 전달의 본문 소비·크기 제한은 별도 계약으로 유지한다.

연결·응답 제한은 전체 검사 제한보다 크게 설정할 수 있다. 실제 요청에서는 각
단계 제한을 남은 전체 검사 시간으로 줄여 적용하며, 전체 검사 제한은 DNS 조회와
모든 리다이렉션을 포함하는 단일 강제 마감 기한이다.

HTTP 전체 기한 만료나 호출자 인터럽트 시 대기 작업과 실제 HTTP 요청을 함께
취소한다. 헤더를 기다리는 요청도 중단할 수 있어야 하며, 헤더를 받은 요청은
본문을 기다리지 않고 닫아 후속 점검이 같은 작업자를 사용할 수 있어야 한다. HTTP 실행기를 닫을 때는 새 작업을 거부하고 실행 중인
요청과 대기 요청을 취소하며, 대기 중인 호출자도 남은 기한을 기다리지 않고 반환한다.

기본 제한은 연결 타임아웃 2초, 응답 타임아웃 3초, 전체 타임아웃 5초,
구성 호환용 응답 바이트 상한 64 KiB, 각각 한 줄당 최대 8 KiB인 응답 헤더 최대 100개, 대기 중인
조회가 최대 8개인 DNS 스레드 2개, 대기 중인 요청이 최대 1개인 HTTP 요청 스레드
1개다. 런타임 설정은 응답 크기 1 MiB, 응답 헤더 200개, 헤더 한 줄당 16 KiB,
대기 중인 조회가 최대 64개인 DNS 스레드 8개, 대기 중인 요청이 최대 16개인
HTTP 요청 스레드 4개를 초과할 수 없다. 검사 선점은 100개, 유지 관리 배치는
1,000개로 제한한다. 이 제한을 비활성화할 수 없다. JVM 리졸버에는 호출별 취소
계약이 없으므로 DNS 조회는 제한된 실행기에서 수행한다. DNS 실행기를 닫을 때
아직 시작하지 않은 대기 조회는 취소하고, 호출자에게 남은 기한을 기다리지 않고
`INTERNAL_FAILURE`를 반환한다. 실행 중인 JVM 리졸버의 강제 중단은 보장하지 않는다.

## 결과 및 상태

영속화하는 결과 분류는 다음으로 제한한다.

- `SUCCESS`: 200~399 범위의 최종 HTTP 응답
- `HTTP_CLIENT_ERROR`: 400~499 범위의 최종 응답
- `HTTP_SERVER_ERROR`: 500~599 범위의 최종 응답
- `DESTINATION_REJECTED`, `DNS_FAILURE`, `CONNECT_TIMEOUT`, `READ_TIMEOUT`,
  `TLS_FAILURE`, `REDIRECT_REJECTED`, `TOO_MANY_REDIRECTS`,
  `RESPONSE_TOO_LARGE`, `NETWORK_FAILURE` 또는 `INTERNAL_FAILURE`

상태는 연속된 확정적 결과로부터 다음과 같이 도출한다.

- 현재 확정적인 검사가 없거나 프로젝션이 오래된 경우: `UNKNOWN`
- 검사 성공: `HEALTHY`, 실패 카운터 초기화
- 대상 검사에 한 번 또는 두 번 연속 실패: `DEGRADED`
- 대상 검사에 세 번 이상 연속 실패: `BROKEN`

`INTERNAL_FAILURE`는 대상의 책임으로 간주하지 않고 상태를 변경하지 않으며
30초 뒤 재시도를 예약한다. 그 밖의 모든 실패는 확정적인 대상 검사 결과다.

모든 선점과 완료 결과는 불변이다. 상태가 바뀐 경우에만 현재 상태 갱신과
상태 변경 이벤트 저장을 같은 DB 트랜잭션에서 처리한다. 오래된 프로젝션
순회도 같은 규칙을 따른다. 이벤트 전송은 이 MVP의 일부가 아니다. PRD-0004가
직접 BATON HTTPS 콜백을 별도로 채택하고 구현한다. BATON은 계속 HTTP를 통해
현재 프로젝션을 조회할 수 있다.

## 보존 및 관측성

- 시도와 결과는 기본적으로 30일 동안 보존한다.
- MVP 시도/결과 정리는 제한된 배치로 삭제하며 현재 프로젝션은 절대로 제거하지
  않는다. 정리 대상은 `FOR UPDATE SKIP LOCKED`로 제한하여 잠긴 행을
  기다리지 않고, 완료 결과가 있는 시도와 결과 없이 버려진 시도를
  별도 후보로 선택한 뒤 유한 부모 시도 삭제로 처리한다. PRD-0004는
  전달 완료된 상태 변경 이벤트에 한해 같은 방식의 제한된 보존 정리를
  별도로 허용한다.
- 오래된 프로젝션 표시와 시도/결과 보존은 서로 독립적인 유지 관리 작업으로
  실행하므로 한 작업의 실패로 다른 작업의 예약이 중단되지 않는다.
- 로그에는 시도 상관관계와 제한된 결과/상태 값을 포함할 수 있지만 원시 URL,
  호스트, 쿼리, 리소스 참조, 조회된 주소, 응답 본문 또는 예외 메시지는 절대로
  포함하지 않는다.
- 더 넓은 애플리케이션 또는 Apache 로거를 DEBUG로 구성해도 Apache HTTP 헤더,
  와이어, 구현 및 TLS 진단 로거 범주는 비활성 상태를 유지한다. Spring JDBC의
  구문 매개변수 로거도 비활성 상태를 유지해 비밀값이나 URL이 바인딩 로그로
  우회하지 못하게 한다. 운영자는 보호된 해당 로거 범주를 재정의해서는 안 된다.
- 예기치 않은 스케줄러 실패는 먼저 Spring의 예약 작업 관측으로 전파된 다음,
  민감정보 제거 오류 처리기가 이를 억제하여 다음 고정 지연 실행이 계속 예약되게 한다.
  Spring Boot 예약 작업 관측 자동 구성은 애플리케이션의 `ObservationRegistry`를
  Spring 예약 작업 등록기에 연결한다. 처리기는 메시지나 스택 트레이스 없이 예외
  클래스만 기록한다.
- 메트릭에는 제한된 결과, 프로토콜, 상태, 예약 클래스/메서드 및 예외 클래스
  레이블만 사용한다. 요청 데이터나 예외 메시지를 사용해서는 안 된다.
- 각 실제 점검은 `baton.watch.check.attempts{outcome}` 카운터와
  `baton.watch.check.duration{outcome}` 타이머에 같은 제한된 결과 분류를
  기록한다. 텔레메트리 기록 실패가 점검 결과나 다음 일정을 바꾸지
  않도록 점검 경계에서 분리한다.
- `baton.watch.check.inflight` 게이지는 현재 URL 점검을 실행 중인 작업 수를
  기록한다. 성공, 제한된 실패, 예기치 않은 예외와 상관없이 점검 호출이 끝나면
  감소하며 식별자 레이블을 사용하지 않는다.
- `baton.watch.check.schedule.delay` 게이지는 현재 선점할 수 있는 점검 중
  가장 오래된 `next_check_at`부터 PostgreSQL 조회 시각까지의 지연을 초 단위로
  기록한다. 활성 리스는 제외하고 처리할 점검이 없으면 0으로 갱신한다. 기존
  `watch_monitor(next_check_at, resource_reference)` 부분 인덱스에서 첫 행만
  읽으며 전체 적체 건수나 식별자 레이블을 추가하지 않는다.
- `baton.watch.check.claimed`, `baton.watch.check.finalizations{status}`,
  `baton.watch.check.lease.recoveries` 카운터는 점유, 완료 처리 상태와 만료
  리스 회수를 영속성 포트 경계에서 기록한다. 배치 중간에 완료 처리가 실패해도
  앞서 발생한 항목의 증거를 잃지 않으며 식별자 레이블을 사용하지 않는다.
- `baton.watch.database.clock.offset` 게이지는 JDBC 왕복 전후 JVM 시각의
  중간점에서 PostgreSQL `clock_timestamp()`를 뺀 부호 있는 초 단위 근사값이다.
- Actuator `scheduledtasks` 엔드포인트는 노출하지 않는다. 런타임 작업 진단은
  내부 기록을 위해 원래 예외를 보존할 수 있지만, 채택된 관리 인터페이스는
  민감정보가 제거된 상태 정보와 Prometheus 출력으로 제한한다.
- Prometheus 레지스트리는 항상 유지하고 관리 포트는 내부에서만 접근한다. WATCH는
  메트릭을 외부 관측 서비스로 직접 전송하지 않는다. 외부 전송을 추가하려면 목적지
  주소 고정, 리다이렉트 금지, 시간·헤더·응답 바이트 상한과 비식별 로그를 포함한
  아웃바운드 안전 경계를 충족하는 별도 결정을 먼저 채택한다.

## 운영자 장애 진단

- Compose의 시작 준비 확인은 `/actuator/health/readiness`를 사용한다. Spring Boot의
  기본 `readinessState`와 `db`를 포함하며, DB 사용 불가 또는 요청 수락 거부 상태는
  HTTP 503을 반환한다. `/actuator/health/liveness`는 DB 상태를 포함하지 않는다.
  두 프로브는 관리 포트에만 두고 상세 상태와 추가 공개 경로는 제공하지 않는다.
- `ops/grafana/watch-overview.json`은 기존 메트릭용 운영 대시보드 템플릿이다.
  DB 적체를 인스턴스 간 합산하거나 수집 누락을 0으로 대체하지 않는다.
  수집기·외부 계정·대시보드 서버·알림 수신 경로를 자동 생성하지 않는다.
- `ops/blackbox/watch-probes.yml`과 별도 Prometheus 템플릿은 WATCH 자체의 내부
  프록시·공개 상태 경로를 확인한다. 60초 주기·5초 요청 제한, 리다이렉트 비추적,
  URL 없는 고정 레이블을 사용한다. HTTP 200뿐 아니라 응답의 `service`가
  `baton-watch`이고 `status`가 `UP`인지 확인하며 실제 배포·관측 시스템 연결은 포함하지 않는다.
  수집 대상이 있는 동안 정상 응답을 2분간 확인하지 못하면 주 경보를 발생시킨다.
  요청 실패·수집 실패·성공 지표 누락이 교차해도 대기 시간을 유지하며,
  수집 성공과 점검 성공이 함께 확인되면 해제한다. 대상 자체의 누락은 별도 5분 경보로 확인한다.

- `ops/staging-monitor-diagnostics.sh`는 지정한 PostgreSQL 컨테이너의 로컬 소켓에
  접속해 한 리소스의 현재 상태와 최근 점검·전달 이력을 JSON으로 출력한다.
  Docker·DB 운영 권한을 이미 가진 운영자용이며 새 HTTP 경로나 권한 체계를 만들지 않는다.
- 두 이력은 각각 기본 50건, 최대 100건을 최신순으로 반환한다. 점검 시도에 결과가
  아직 없으면 결과 필드는 `null`이다. 없는 리소스는 상태 `null`과 빈 이력을 반환한다.
- 점검 분류·HTTP 상태·소요 시간과 전달 분류·시도 횟수·다음 재시도 시각을 포함한다.
  원본 URL, 호스트, 응답 본문, 리소스 참조와 리스 토큰은 출력하지 않는다.
- 읽기 전용 트랜잭션과 기존 리소스별 인덱스를 사용하고 SQL 5초·잠금 대기 1초·
  트랜잭션 10초로 제한한다. 이력 보존 기간은 바꾸지 않는다.
- 리소스 참조와 조회 건수는 SQL 본문과 분리해 바인딩한다. 진단 트랜잭션에서
  PostgreSQL의 정상·오류 구문 로그에 매개변수 값을 기록하지 않도록 설정하며,
  이 설정을 적용할 수 없으면 조회 전에 실패한다. 다른 연결의 로그 설정은 바꾸지 않는다.

## 인수 기준

1. 유효한 활성 모니터를 동기화하면 `UNKNOWN` 프로젝션을 반환하고 즉시 검사 대상이 된다.
2. 오래된 리비전과 같은 리비전의 충돌이 현재 상태를 덮어쓸 수 없다.
3. 백그라운드 워커는 네트워크 I/O 중에 트랜잭션을 유지하지 않고 작업을 선점한다.
4. 성공한 최종 응답은 불변 시도/결과 레코드와 `HEALTHY`를 생성한다.
5. 연속된 세 번의 실패는 `DEGRADED`를 거쳐 `BROKEN`을 생성한다.
6. 상태 변경과 그에 따른 내구성 있는 이벤트는 원자적으로 커밋된다.
7. 전역 주소가 아니거나 모호한 목적지는 리디렉션 이후를 포함하여 연결 전에 거부된다.
8. 확정을 반복하거나 리스를 잃어도 결과가 중복되거나 더 최신 프로젝션을 덮어쓰지 않는다.
9. 인증된 조회 경로는 문서화된 프로젝션만 노출한다.
10. 현재 실행 중인 점검 수, 가장 오래된 선점 가능 점검의 일정 지연, 점유·완료
    처리·만료 리스 회수와 JVM-PostgreSQL 시계 편차를 식별자 없이 관측할 수 있다.
11. 점검 중지 시 점검 예약만 제외하고 API·전달·유지보수를 유지한다.
12. 운영 진단은 조회 건수와 시간을 제한하고 데이터를 변경하거나 민감한 대상 정보를 출력하지 않는다.

13. 큰 본문·스트리밍 본문을 기다리지 않고 헤더로 판정하며, 헤더 상한과 연결 종료를 유지한다.
14. 재점검의 중복·경합·30초 경계와 비활성·없는 리소스 거부를 검증한다.
