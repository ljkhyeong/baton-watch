# 운영 기본 설정의 용량 참고 시험

## 목적과 실행

`capacityTest`는 실제 Spring Boot·PostgreSQL·예약 작업을 사용하며 운영 기본값인
점검 배치 1건, 폴링 1초, 일반 점검 간격 60초와 유지보수 배치 100건을 유지한다.
외부 점검만 대역으로 바꿔 네 건 중 한 건은 5초 후 `READ_TIMEOUT`, 나머지는
100ms 후 성공하도록 구성한다. 실제 DNS·TLS·네트워크 처리량 시험은 아니다.

```bash
./gradlew :bootstrap:capacityTest --no-daemon
./gradlew :bootstrap:capacityTest -PwatchCapacityMonitors=30 --no-daemon
./gradlew :bootstrap:capacityTest -PwatchCapacitySlowMillis=100 --no-daemon
```

Java 21과 실행 중인 Docker가 필요하다. 모니터 수는 기본 12개·허용 4~30개,
느린 점검의 대역 지연은 기본 5000ms·허용 100~5000ms다. 일반 `test`와 분리된
수동 시험이며 운영 설정·데이터를 수정하지 않는다. 전체 제한은 4분이고, 모든 모니터가
두 번 이상 완료되는지 최대 3분 기다린다. 이 제한은 지원 규모나 운영 SLO가 아니다.

## 측정하는 값

- `firstPassSeconds`: 등록 시작부터 모든 모니터의 첫 점검이 끝날 때까지의 시간
- `maximumIntervalSeconds`: 같은 모니터의 연속 완료 시각 사이에서 관찰한 최대 간격
- `purgeRows`, `purgeMillis`: 보존 정리 한 번의 삭제 건수와 처리 시간

31일 전의 만료 이력을 모니터마다 120건 삽입해 점검과 유지보수가 함께 실행되게 한다.
이는 30일치 분 단위 이력 전체가 아닌 제한된 표본이다. 12개 시험은 1440건,
30개 시험은 3600건이다. 예약 유지보수 뒤에도 남아 있는 표본에서 단일 정리 호출이
100건까지만 삭제하는지 확인한다. 전체 대용량 보존 정리의 성능을 증명하지 않는다.

보고서는 `bootstrap/build/reports/tests/capacityTest/index.html`과
`bootstrap/build/test-results/capacityTest/`에 기록한다. 같은 작업을 다시 실행하면
이전 로컬 보고서는 바뀌므로 필요한 결과는 별도로 보관한다.

## 용량 판단

60초 설정은 완료 후 다음 예정 시각까지의 간격이다. DB 대기, 점검 실행 시간과
이미 도래한 다른 모니터 처리 시간도 실제 완료 간격에 포함된다. 배치 1건에서는
항목 처리 후 1초를 쉬므로, 모든 요청이 5초 걸린다고 가정하면 DB 시간을 제외해도
한 인스턴스가 처리하는 상한은 약 10건/분이다. 응답이 빨라도 폴링 비용이 남는다.

먼저 지원 모니터 수와 허용 일정 지연을 정하고 기본 설정으로 측정한다. 처리량이
부족하면 기존 리스·허용 실행 시간 검증을 통과하는 배치 조정 또는 인스턴스 확장을
측정한다. HTTP 스레드 수만 올려도 직렬 점검 서비스가 자동으로 병렬화되지는 않는다.

이력은 모니터 1000개가 매분 한 번씩 30일간 점검되면 시도 약 4320만 건과 같은 수의
결과를 만든다. 이는 간격과 건수에 따른 계산 예시이며 현재 지원 규모가 아니다.
실제 평균 행·인덱스 크기, 백업 공간과 보존 정리 속도를 함께 산정해야 한다.
기본 정리는 인스턴스당 호출마다 최대 100건이고 호출 간격은 1분 이상이다.
생성량이 정리량을 지속적으로 넘지 않는지, 미전달 이벤트 증가까지 포함해 검증한다.
