# 격리 DB 부하·장애 복구 시험

이 시험은 운영 DB와 외부 URL을 입력받지 않는다. Testcontainers의 임시
PostgreSQL 18.6에 실제 Flyway 마이그레이션을 적용하고 application 유스케이스와
JDBC 어댑터를 실행한다. 유료 서비스나 새 런타임 의존성은 사용하지 않는다.

## 실행

Java 21과 실행 중인 Docker가 필요하다.

```bash
./gradlew :adapter-out-persistence:loadTest --no-daemon
./gradlew :adapter-out-persistence:loadTest -PwatchLoadMonitors=500 --no-daemon
```

모니터 수는 기본 100개, 허용 범위는 1~1000개다. 각 실행은 점검 대역 지연
0ms와 20ms 두 사례를 수행한다. 사례별 제한은 3분이다. 시간 초과는 해당 환경에서
시험이 끝나지 않았다는 뜻이며 서비스 SLO 위반 판정이 아니다. 일반 `test`와
분리해 매번 실행하며, CI에서는 25개짜리 복구 스모크를 별도로 실행한다.

## 확인하는 흐름

1. 활성 모니터를 순차 동기화해 처리할 일정을 만든다.
2. 백로그 요약 행을 잠가 첫 점검의 완료 처리를 실패시킨다. 완료 트랜잭션이
   롤백되고 이미 점유한 시도는 남는지 확인한다.
3. 시험 DB에서만 리스 만료 시각을 당기고 단일 작업 스레드으로 점검을 재개한다.
   모니터마다 결과가 한 건씩 확정되고 실패한 시도도 이력에 남는지 확인한다.
4. 콜백 대역이 모두 `503`을 반환하도록 해 이벤트가 소실되지 않고 재시도
   상태로 유지되는지 확인한다.
5. 시험 DB에서만 재시도 시각을 당긴 뒤 콜백 대역을 `204`로 바꾼다. 재시도
   전후 페이로드가 같고 최종 백로그가 0인지 확인한다.

외부 호출 대역은 트랜잭션 밖에서 실행되는지도 확인한다. 실제 대기 대신 시험
데이터의 시각을 조정하므로 운영 재시도 간격이나 리스 설정을 완화하지 않는다.
시간 계산에는 사례 시작 시점에 고정한 `Clock`을 사용한다.

## 결과 해석

표준 출력과 `adapter-out-persistence/build/reports/tests/loadTest/index.html`에서
동기화, 점검·DB 복구, 전달 실패·복구 소요 시간과 최대 실제 적체 지연을 확인한다.
별도 결과 문서에는 코드 SHA, 장비·Docker 자원, 모니터 수와 이 집계값만 기록한다.

이 시험은 작업을 한 건씩 연속 실행하며 운영 폴링 간격은 재현하지 않는다.
HTTP 서버·인증·DNS·실제 HTTP 클라이언트·운영 Hikari 풀·프로세스 재시작·네트워크
단절은 측정하지 않는다. 따라서 지원 모니터 수나 처리량 보증으로 사용하지 않는다.
별도 JVM의 실제 강제 종료와 기본 리스의 자연 만료 후 복구는
[프로세스 복구 시험](process-recovery-test.md)에서 확인한다.
공개 배포 전에는 승인된 환경에서 실제 동기화 요청 폭주, 느린 대상, DB 연결
장애, 콜백 장기 장애와 회복을 별도로 시험하고 지원 규모·SLO를 정해야 한다.
