# 공개 요청 속도 제한

`compose.staging-tunnel.yml`의 `watch-gateway`와 `ops/nginx/watch-gateway.conf`는
공개 배포 전 검증할 NGINX 구성이다. 실제 터널이나 공개 서비스를 생성하지 않는다.

## 기본값

| 대상 | 지속 요청량 | 추가 버스트 | 초과 응답 |
| --- | --- | --- | --- |
| `/api/v1/system/status` | 초당 10건 | 20건 | 429 |
| 나머지 `/api/v1/` | 초당 5건 | 10건 | 429 |

NGINX `limit_req`의 누수 버킷 방식이며 버스트는 지연 없이 통과시킨다.
클라이언트별 제한이 아니라 프록시 인스턴스 한 개의 경로 그룹별 전체 예산이다.
IP·헤더·토큰·리소스 참조를 키로 사용하지 않는다. 값을 바꾸려면 설정 파일을
검토·커밋하고 다음 격리 검사와 예상 부하 검사를 다시 실행한다. 수치는 SLO가 아니다.

```bash
./ops/tests/staging-compose-policy-test.sh
python3 ops/tests/gateway-test.py
```

실제 NGINX와 HTTP 대역을 임시 Compose 프로젝트에서 시작하고 호스트 루프백의
임시 포트로 호출한다. 상태·모니터 그룹 각각의 429와 독립 예산, 인증 헤더 전달,
큰 본문의 인증 전 프록시 거부 방지, 관리 경로 차단, 민감 값 없는 로그를 확인한다.
WATCH 자체 인증·본문 처리의 근거는 별도의 HTTP·전체 조립 테스트다.
프록시 연결 제한은 2초, 응답 읽기 간격 제한은 65초다. DB 연결 대기와 트랜잭션에
각각 허용된 최대 30초를 고려한 값이며 전체 요청 기한이나 처리량 보장은 아니다.
종료 시 시험 컨테이너·네트워크만 정리하며 운영 DB나 콜백은 사용하지 않는다.

## 승인 뒤 적용

1. 기존 서버에 NGINX 한 개의 자원 여유를 확인한다. 컨테이너 상한은 CPU 0.25,
   메모리 64 MiB, PID 32, 임시 공간 16 MiB다. 새 유료 서비스는 신청하지 않는다.
2. [스테이징 배포 절차](staging-deployment.md)의 두 Compose 파일을 함께 사용한다.
   `cloudflared` → `watch-gateway:8080` → `watch:8080` 순서다. 터널은
   `watch-ingress`, WATCH는 `watch-edge`에 있으므로 직접 우회 연결하지 않는다.
3. 원격 터널의 상태·모니터 규칙을 `http://watch-gateway:8080`으로 변경한다.
   `/actuator`나 NGINX 루프백 상태 포트 8082를 원격에 노출하지 않는다.
4. 먼저 평상시 공개 200·401·404 스모크를 통과시킨다. 승인된 시험 시간에 상태와
   미인증 모니터 요청을 각각 제한보다 빠르게 보내고 429 및 `RATE_LIMITED` JSON,
   `Cache-Control: no-store`를 외부 HTTPS에서 확인한다. 운영 리소스·토큰을 쓰지 않는다.
   요청을 줄인 뒤 200·401 복구와 두 그룹의 독립성도 확인한다.
5. 정한 동기화·조회 부하가 제한에 막히지 않는지와 프록시 CPU·메모리·로그 회전을
   확인하고 운영자 승인과 증거를 남긴다. 시험 도구가 통과해도 이 단계는 생략하지 않는다.

NGINX는 인증을 하지 않으므로 제한 초과 시 미인증 요청도 401 대신 429를 받을 수
있다. 제한을 통과한 요청은 기존 WATCH 인증·본문 계약을 따른다. 관리 포트를
열거나 DB·점검기 제한을 완화해 프록시 실패를 우회하지 않는다.

설정 파일은 읽기 전용 바인드 마운트이므로 배포 커밋의 체크섬과 내용을 보관한다.
교체 후 `staging_compose up -d --no-deps --force-recreate watch-gateway`로 재생성한다.
기본 Docker unhealthy 상태는 자동 재시작을 뜻하지 않는다. 요청 처리 실패는
접근 로그의 상태 코드와 프록시·WATCH 준비 상태를 함께 확인한다.

프록시 자체 생존 확인과 실제 요청 경로의 장애는 다르다. 상시 요청 경로 감시에는
[인바운드 점검 템플릿](ingress-monitoring.md)을 승인된 기존 수집 환경에 적용한다.

## 롤백

먼저 터널을 중지한다. 이전에 검증한 NGINX 이미지 다이제스트와 설정, 해당 커밋의
네트워크 정의를 복원하고 로컬 정책·프록시 검사를 통과시킨 뒤 터널을 재개한다.
NGINX 도입 전 리비전으로 되돌릴 때는 원격 서비스 주소와 네트워크도 달라진다.
요청 제한이 사라진 공개 서비스는 재개하지 말고 별도 승인된 제한 대안을 먼저 마련한다.
