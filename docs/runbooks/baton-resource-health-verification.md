# BATON 자료 상태와 재점검의 공개 HTTPS 검증

확인일: 2026-09-05

## 현재 검증 상태

지정된 `https://watch-staging.b4ton.com`에 `ops/staging-public-smoke.sh`를 실행했으나
DNS 조회 실패(`curl` 종료 코드 6)로 첫 상태 요청을 보내지 못했다. 실행 환경의 네트워크
제한 밖에서도 같은 결과였다. 이는 HTTPS·서비스 인증·상태 갱신을 통과했다는 증거가 아니다.
BATON 스테이징 주소, 전용 시험 자료와 인증 설정 파일도 현재 작업 환경에는 제공되지 않았다.

## 준비할 환경

- 유효한 공개 HTTPS로 접근 가능한 BATON과 WATCH 스테이징. WATCH는 재점검 API를
  제공하는 `3a04e7b` 이상, BATON은 조회 분산·실패 안내·점검 제외 사유와 역할 이동 후
  대기시간 유지가 반영된 `f103dd9` 이상을 사용한다.
- 전용 시험 팀·진행 중인 시즌·역할과 공개 URL 자료. 실제 운영 자료나 공유 키를 시험에 사용하지 않는다.
- BATON 공유 키와 서로 분리된 WATCH API·이벤트 수신 토큰의 소유자 전용 설정 파일.
  토큰·공유 키·대상 URL을 터미널 출력, 화면 녹화, 요청 목록 내보내기나 보고서에 남기지 않는다.
- 두 서비스의 배포 리비전, 비공개 관리 지표와 읽기 전용 DB 진단 접근.
  재시작·통신 단절은 다른 사용자가 없는 전용 스테이징에서 수행한다.

## 확인 순서

1. [공개 스테이징 전달 사전 점검](public-staging-event-delivery.md)의 DNS·TLS·상태·인증
   조건을 통과시킨다. 통과 전에는 인그레스나 WATCH의 공개 목적지 정책을 완화하지 않는다.
2. BATON UI에서 시험 자료를 저장하고 BATON 아웃박스 전달 완료와 WATCH의 같은
   `resourceReference`·`sourceRevision`·`ACTIVE`를 확인한다. 직접 WATCH에 만든 모니터만으로
   BATON 원본 변경부터의 연동을 검증했다고 보지 않는다.
3. 아래 표의 화면 동작을 두 브라우저에서 확인한다. 동일 자료의 조회 공유는 같은 BATON
   인스턴스에서 요청이 실제로 겹쳤을 때만 기대한다. 완료 응답을 장기 캐시하는 기능은 없다.
4. WATCH를 한 번 재시작한 뒤 기존 모니터와 일정·결과가 남고 점검이 재개되는지 확인한다.
   BATON 상태 조회는 정상으로 돌아와야 하며 링크와 원본 자료는 계속 남아야 한다.
5. 전용 스테이징에서 BATON→WATCH 통신만 일시 차단한다. 자료 화면과 다른 작업이 유지되고
   상태만 확인 불가로 표시되는지 확인한다. 차단 해제 뒤 후속 조회로 수렴하는지 확인한다.
   콜백 중복 전달·미전달 이벤트 보존은 위 전달 절차로 별도 검증한다.

| 사례 | 기대 결과 |
| --- | --- |
| 같은 역할의 자료 8개 열기 | 브라우저 상태 GET은 동시 최대 2건·최소 250ms 시작 간격이며 모든 결과를 차례로 표시 |
| 상태 조회 중 상세 닫기·다시 열기 | 닫힌 상세의 대기·진행 조회 취소, 재개 후 해당 자료 결과 표시 |
| 두 브라우저에서 같은 자료 동시에 조회 | 각 요청은 권한 확인을 거치며 겹친 원격 GET만 공유 |
| 재점검 접수 | 결과를 미리 정상으로 바꾸지 않고 접수 안내·30초 버튼 대기 표시 |
| 429와 `Retry-After` | 서버가 지정한 초 동안 버튼 비활성화, 대기 종료 뒤 재요청 가능 |
| 재점검 응답 대기 중 다른 역할을 보고 복귀 | 같은 자료는 요청 중 표시 유지, 다른 자료는 사용 가능 |
| 재점검 대기 중 다른 역할을 보고 복귀 | 같은 자료의 남은 대기시간 유지, 지정 시간이 지나면 재요청 가능 |
| 같은 점검 시각의 후속 응답 | 접수 안내 유지 |
| 더 새로운 `AVAILABLE` 결과 | `새 점검 결과를 확인했습니다.` 표시. 특정 요청의 시도 ID를 확인했다는 뜻은 아님 |
| 조회 불가·5분 이상 오래된 결과 | 새 결과 확인으로 처리하지 않고 링크 유지 |
| 최근 DNS·연결 실패 결과 | 실패 원인과 WATCH가 계산한 연속 실패 횟수 표시 |
| 점검 서비스 내부 오류 | 대상 링크의 새 실패가 아니라는 안내와 기존 실패 횟수 유지 |
| 실패 뒤 새 정상 결과 | 이전 실패 원인과 횟수 안내 제거 |
| 바통 전달·수정 충돌 복구 대기로 편집 제한 | 상태 조회 유지, 서버 결과 표시, 다시 점검 버튼 숨김 |
| 종료 시즌·감시 일시 중지·URL 조건 미충족 | `자동 점검 대상 아님`과 서버가 판단한 구체적인 사유 표시 |
| 최초 등록 정보 없음·주소 반영 대기 | `PENDING/SYNC_PENDING`에 따라 동기화 대기 안내, 재점검 버튼 숨김 |
| URL 변경·자료 보관·공유 키 폐기 | 이전 결과로 권한이나 원본 변경을 가리지 않음 |

429는 기존 일정에 합류하면 발생하지 않을 수 있다. 전용 시험에서 새 예약이 한 번 처리된 뒤
다음 일정이 미래인 상태에서 30초 안에 다시 앞당기는 조건을 만들고 확인한다. 운영 DB의
일정이나 쿨다운 시각을 직접 수정하지 않는다.

## 남길 증거

두 서비스의 배포 리비전, 검사 UTC 시각, 사례별 성공·실패, HTTP 상태·고정 오류 코드와
관찰한 점검 시각을 기록한다. 요청별 인증 헤더·본문 전체나 원본 URL은 수집하지 않는다.
모의 HTTP와 로컬 브라우저 검사는 공개 DNS·TLS·실제 자격 증명·재시작 검증과 구분한다.
WATCH DB의 독립 복원은 [불변 스냅샷 복원 절차](baton-snapshot-recovery.md)를 따르며
단순 재시작 성공으로 대체하지 않는다.
