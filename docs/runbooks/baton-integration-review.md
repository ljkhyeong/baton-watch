# BATON 상태 표시와 독립 복원 구현 확인

확인일: 2026-09-05

BATON `40b46ea78e0a97a52f4caa0f4d00145935b69e5c` (`codex/watch-state-recovery`)에 역할 자료 상태 조회·수동 재점검 UI와 후속 보완을 반영했다. 최신성은 연결 판정 시각으로 확인하고, 점검 시도 시각은 별도로 표시한다. 오프라인·조회 캐시 만료 표시와 탭 복귀·재연결 재조회, 수동 상태 조회도 제공한다. 접수·새 결과 확인 안내를 역할 이동 뒤에도 유지하며 수동 조회와 표시 상태 변경을 스크린리더 알림 영역에 전달한다.
WATCH에는 최신 불변 BATON 스냅샷의 대조·재전송 도구를 추가했다. 아래 내용은 저장소 구현과
로컬 검증 결과이며 공개 운영 활성화나 실제 콜백 전달의 증거가 아니다.

## 역할 자료 상태 표시

BATON은 원본 변경과 같은 트랜잭션의 불변 아웃박스, 별도 비동기 전달·재시도·만료 리스 복구,
원본과 자체 아웃박스의 정기 보정, 상태 이벤트의 불변 인박스를 유지한다.

새 화면은 이벤트를 상태 순서대로 재생하지 않는다. 워크스페이스 프로젝션과 별도 GET으로
WATCH의 현재 상태를 조회하고 다음 경계를 적용한다.

- 조회 전후에 팀·시즌·자료 소유권·공유 키와 최신 아웃박스의 URL을 확인한다.
  네트워크를 기다리는 동안 DB 트랜잭션을 유지하지 않는다.
- 원격 리비전·감시 상태 불일치 또는 누락은 `UNKNOWN/PENDING`, 조회 장애와 동시성 한도는
  `UNKNOWN/UNAVAILABLE`이다. 연결 판정 `lastConclusiveAt`이 없으면 `UNKNOWN/PENDING`,
  5분 전이거나 더 오래된 판정은 `UNKNOWN/STALE`이다. 판정이 있는데 시도가 없거나,
  시도가 미래이거나, 판정이 시도보다 뒤여도 `STALE`이다. 내부 오류로 시도 시각만
  갱신돼도 이전 판정의 유효 기간은 늘어나지 않는다. WATCH 자체의 기본 10분 상태 만료는 유지한다.
- 보관 자료·종료 시즌·연동 또는 감시 중지·비활성 최신 스냅샷은 점검 대상에서 제외한다.
  WATCH 상태가 BATON 자료의 존재나 접근 권한을 결정하지 않는다.
- `monitoringReason`으로 연동 중지·감시 일시 중지·시즌 종료·보관·URL 조건 미충족·감시
  비활성을 구분한다. 최초 등록 정보가 없거나 현재 주소와 맞지 않는 자료는 `PENDING`과
  `SYNC_PENDING`을 반환하고 `점검 서비스 동기화 대기`로 표시한다. 권한·소유권 확인 뒤에
  사유를 판단하며, 등록이 완료되기 전에는 재점검을 보내지 않는다.
- 별도 클라이언트는 조회 연결 3건과 재점검 POST 연결 1건을 분리한다. 조회 호출자는
  중복 합류를 포함해 최대 32명, 연결 대기는 최대 1초다. 같은 자료의 진행 중인 GET을
  공유하고 합류자는 최대 4초 기다린다. 완료 결과는 캐시하지 않으며 POST에는 대기열이 없다.
  연결 1초·읽기 2초, 응답 8KiB와 리디렉션 금지는 유지한다.
- 열린 역할 상세는 자료별 상태·최근 연결 판정 및 점검 시도 시각·다시 점검 버튼을 표시하며 30초마다
  조회한다. 브라우저별 GET은 동시 2건·최소 250ms 시작 간격, 대기 최대 100건·대기부터 응답까지
  30초 상한이다. 실제 전송에는 기존 API 클라이언트의 10초 상한도 적용한다.
  백그라운드 주기 조회는 하지 않는다. 상세를 닫으면 대기·진행 조회를 취소한다.
  오프라인·조회 일시 중지·30초 조회 캐시 만료 시 이전 상태 배지와 실패 원인·횟수를
  현재 결과로 표시하지 않고 새 결과 확인 여부도 갱신하지 않는다. 이미 확인한 안내는
  별도로 유지한다. 조회 오류가 없는 기존 캐시의
  판정·시도 시각과 원본 링크는 유지한다. 조회 오류가 나면 이전 응답의 상세 정보도 숨긴다.
  탭 복귀·재연결 때 GET을 다시 보내고, `상태 다시 조회`로도 같은 조회를 수행한다. 진행
  중인 GET을 취소·재시작하지 않으며 기존 조회 대기열과 제한을 사용한다. 오프라인·조회
  중에는 조회 버튼을 잠그고, 오프라인·캐시 만료 중에는 URL 재점검도 비활성화한다.
  상태 조회 버튼은 URL 재점검을 접수하거나 재점검 대기시간을 바꾸지 않는다.
  자료 이름을 포함한 스크린리더 알림 영역은 수동 조회의 진행·결과를 알리고, 자동 조회는
  표시 상태·점검 제외 사유가 바뀔 때만 알린다. 같은 상태나 시각·횟수만의 변경은 반복해서
  알리지 않는다. 상세가 닫히면 실시간 알림을 끈다.
  서버의 5분 판정과 별도로 캐시 표시 여부만 제한하며 서버 응답과 공용 캐시 설정은 변경하지 않는다.
- 바통 전달·수정 충돌 복구 대기로 편집이 잠겨도 연결 상태는 조회한다. 수동 재점검 버튼은
  기존대로 숨기며 `상태 다시 조회`는 허용한다. 자동 점검 대상 여부는 편집 제한에서
  추측하지 않고 서버 응답을 따른다.
- 현재 원본과 일치하는 최근 결과에는 `lastOutcome`와 `consecutiveFailures`를 전달한다.
  `AVAILABLE`이 아니면 두 값은 `null`이다. 화면은 고정 코드에 맞는 실패 원인과 양수인
  연속 실패 횟수를 표시하고 정상 결과가 오면 지운다. 점검 서비스 내부 오류는 대상 링크의
  새 실패를 뜻하지 않으며 WATCH가 보존한 기존 횟수를 그대로 표시한다.
- 수동 재점검은 현재 원격 리비전과 자료를 다시 확인해 동기화가 덜 된 요청을 보류한다.
  접수와 완료를 구별하고 WATCH의 429 대기 초를 전달한다. GET과 POST 사이의 동시 변경을
  원자적으로 막는 새 계약은 아니며 원본 아웃박스가 최종 감시 목표로 수렴시킨다.
  접수 후 버튼을 30초, 429이면 서버 대기 초 동안 비활성화하고 남은 초를 표시한다.
  재요청 시각과 진행 중인 요청은 팀·시즌·자료·공유 키·URL별로 구분해 역할 이동 뒤에도
  유지한다. 미사용 재요청 시각 캐시는 1시간 뒤 정리하며 현재 페이지 메모리만 사용한다.
  페이지 전체 새로고침이나 다른 브라우저의 대기시간까지 보존하는 기능은 아니다.
  이전보다 새로운 `lastConclusiveAt`의 `AVAILABLE` 결과가 조회되면 접수 안내를 바꾼다.
  이전 판정이 없었다면 최초 판정을 확인한다. 내부 오류로 시도 시각만 바뀌거나 같은 판정
  시각·조회 실패인 응답은 새 결과로 처리하지 않는다. 특정 요청의 점검 시도 ID를 확인했다는 의미는 아니다.
  접수 내용과 새 결과 확인 여부도 같은 자료 범위의 메모리 캐시에 보관하고 미사용 캐시는
  1시간 뒤 정리한다. 역할 이동 뒤 유지하며 한 번 확인한 안내는 오프라인·조회 실패·캐시
  만료로 접수 대기로 되돌리지 않는다. 새 재점검을 시작하거나 URL·공유 키가 바뀌면 이전
  안내를 초기화한다. 페이지 전체 새로고침이나 다른 브라우저까지 안내를 보존하지 않는다.

`eventId`는 중복 제거용이며 `sourceRevision`은 BATON 목표 스냅샷 번호다. 어느 것도 같은
스냅샷에서 발생한 상태 변경의 순번으로 사용하지 않는다. 인박스는 고유 이벤트를 계속 보존하고
UI는 이 인박스를 적용하지 않으므로 역순 이벤트로 최신 상태를 덮지 않는다. `healthRevision`
필드나 별도 상태 저장 테이블은 추가하지 않았다.

## WATCH 독립 복원

BATON의 정기 보정은 자체 아웃박스와 원본을 비교한다. WATCH DB만 과거로 복원해 이미 전달한
모니터가 사라져도 정기 보정만으로는 이를 알 수 없으므로
[불변 스냅샷 대조·재전송 절차](baton-snapshot-recovery.md)를 사용한다.

`ops/export-baton-watch-snapshots.sql`은 BATON MySQL에서 자료별 마지막 불변 아웃박스를 읽기
전용으로 내보낸다. `ops/reconcile-baton-snapshots.py`는 기본 조회 모드로 차이를 보고하고,
검토한 파일 해시를 지정한 재전송 모드에서 같은 원본 리비전과 본문을 PUT한다.
더 높은 원격 리비전이나 같은 리비전의 다른 본문은 자동으로 덮어쓰지 않는다.
BATON 원본·아웃박스 전달 상태·WATCH 미전달 이벤트를 삭제하거나 직접 수정하지 않는다.

GET이 URL을 노출하지 않으므로 리비전 일치만으로 전체 본문 일치를 주장하지 않는다.
같은 리비전의 PUT 200까지 확인해야 URL 일치가 검증된다. WATCH에만 남은 참조나 유실된
과거 이력·이벤트를 복원하는 도구는 아니다.

## 검증과 배포 순서

이번 프런트 보완은 타입 검사·프로덕션 빌드와 기능별 브라우저 75개를 통과했다.
Chromium·390px 모바일·WebKit에서 접수 응답 대기 중 역할을 이동한 경우와 응답 뒤 복귀한
경우의 접수 안내 보존, 새 결과 확인 뒤 오프라인·조회 불가·역할 이동, 새 재점검과 실제
자료 URL 수정 뒤 안내 초기화를 확인했다. 수동 조회의 진행·확인 불가·정상 알림과
동일 상태의 자동 조회 중 알림 텍스트 불변, 정상→실패 변경 알림도 확인했다.
기존 판정·시도 시각 구분, 429·대기시간, 점검 제외 사유, 조회 분산·닫기 취소,
오프라인·탭 복귀·재연결과 수동 상태 조회도 포함한다.

집중 18개 중 15개가 먼저 통과했다. URL 변경 사례는 시험 도구가 반환한 복사본을 수정해
변경이 반영되지 않았으므로 실제 자료 수정 화면을 사용하는 방식으로 고쳤다. 해당 3개를
다시 통과한 뒤 기능 전체 75개를 한 워커로 실행해 모두 통과했다.
검증은 모의 HTTP 응답과 로컬 브라우저를 사용했다. 접근성은 알림 영역의 속성·텍스트 변경을
확인했으며 실제 VoiceOver·NVDA 낭독이나 공개 HTTPS·실제 기기 검증을 대신하지 않는다.

이번에는 프런트 기능과 문서만 변경해 백엔드·API 계약 검사를 다시 실행하지 않았다.
서버 판정 시각 변경인 `2296c4c`에서 전체 일반 테스트 754개·REST Docs 159개·전체 빌드와
생성 API 계약 검사를 통과했다. 앞선 `fdd2c32`에서는 전체 브라우저 455개가 통과하고
기존 프로젝트별 설정에 따라 43개가 제외됐다. 이번에는 기능별 75개만 실행했으며 앱 전체
브라우저를 다시 실행하지 않았다.

WATCH 복구 도구는 이전 `20d276e` 작업에서 회귀 7개와 실제 MySQL V16 스키마의 최신 두
스냅샷 내보내기·원본 세 행 불변을 검증했다. 이번 WATCH 변경은 문서뿐이며 애플리케이션과
복구 도구 테스트를 다시 실행하지 않았다. 위 결과는 모의 HTTP 응답과 폐기 가능한 로컬 DB,
로컬 브라우저의 증거이며 공개 HTTPS를 검증한 결과가 아니다.

WATCH 재점검 API와 본문 없는 대상 GET은 `3a04e7b`부터 제공한다. BATON 상태 UI를 활성화할
환경에는 이 계약을 먼저 배포하고 서비스 전용 토큰을 설정한다. 새 화면은 `lastConclusiveAt`
필드가 없는 응답을 조회 불가로 처리하므로 BATON API를 프런트보다 먼저 배포한다. BATON에 남아 있던 64KiB
본문 때문에 정상 문서를 실패로 볼 수 있다는 문구도 최신 동작으로 수정했다.
공개 HTTPS, 실제 자격 증명, 콜백 중복 전달·적체 해소와 운영 복원 훈련은 별도 확인이 필요하다.

2026-09-05 지정된 `watch-staging.b4ton.com`의 공개 스모크는 네트워크 제한 밖에서도 DNS
조회에 실패했다. BATON 스테이징 주소·시험 자료·인증 설정 파일은 제공되지 않아 실제 서비스
간 검증을 진행하지 못했다. 준비 조건과 재시작·통신 단절·화면 확인은
[공개 HTTPS 검증 절차](baton-resource-health-verification.md)에 기록했다.
