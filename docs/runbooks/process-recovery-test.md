# 별도 JVM 중단·재시작 복구 시험

이 시험은 Testcontainers가 만든 임시 PostgreSQL과 테스트 전용 자식 JVM만 사용한다.
운영 DB·외부 URL·배포 자격 증명을 입력받지 않으며 유료 서비스나 새 의존성을
추가하지 않는다. 기존 application 서비스와 JDBC 어댑터는 그대로 실행한다.

## 실행

Java 21과 실행 중인 Docker가 필요하다.

```bash
./gradlew :adapter-out-persistence:processRecoveryTest --no-daemon
```

일반 `test`와 분리하여 매번 실행하며 CI에서도 필수로 실행한다. 점검 리스 30초,
전달 리스 60초를 실제로 기다리므로 세 사례의 리스 대기만 약 150초다.
각 사례의 제한은 2분이다. DB 시각이나 리스 만료 시각을 강제로 앞당기지 않는다.

## 확인하는 흐름

| 중단 지점 | 중단 직후 확인 | 새 JVM에서 확인 |
| --- | --- | --- |
| 점검 점유 커밋 후 외부 호출 경계 | 시도는 남고 결과는 없으며 유효 리스를 다른 작업자가 점유할 수 없음 | 자연 만료 후 새 시도로 완료하고 결과·상태 변경 이벤트가 각각 한 건 생성됨 |
| 전달 점유 커밋 후 요청 전 | 이벤트와 백로그가 남고 수신 요청은 없음 | 자연 만료 후 전달, 전달 시도 2회·백로그 0 |
| 수신 대역이 요청을 받은 뒤 응답 전 | WATCH는 이벤트를 `PENDING`으로 보존 | 자연 만료 후 동일 이벤트 ID·페이로드로 재전달, 최종 `DELIVERED` |

부모 시험은 `ProcessBuilder`로 별도 Java 프로세스를 만들고 점유 완료 신호나
수신 요청을 확인한 뒤 `destroyForcibly()`로 실제 종료한다. Linux와 macOS에서는
강제 종료에 해당하며 Spring 컨텍스트를 닫거나 예외만 던지는 방식이 아니다.
새 JVM은 기존 작업자 서비스를 1초 간격으로 호출하여 리스 회수를 기다린다.
시간을 사용하는 서비스에는 자식 JVM 시작 시점의 고정 `Clock`을 주입하며,
실제 리스의 기준 시각과 만료 판정은 기존 PostgreSQL 선점 쿼리가 담당한다.

시험용 콜백은 부모 JVM의 루프백 임의 포트에만 바인딩한다. 첫 응답을 보류한
상태에서 자식 JVM을 종료하고, 두 번째 요청에는 `204`를 반환한다.
`Idempotency-Key`와 전체 페이로드 값의 동일성을 비교한다. 시험이 끝나거나
실패하면 자식 JVM, HTTP 서버·실행기를 정리하고 임시 DB는 Testcontainers가 정리한다.

## 증거와 한계

결과는 `adapter-out-persistence/build/reports/tests/processRecoveryTest/index.html`과
같은 작업의 JUnit XML에 남는다. CI는 이 스위트에 실행된 테스트가 있고
실패·오류·건너뜀이 없는지 확인하며 보고서를 7일 보관한다.

이 시험은 운영 부트 JAR이나 Spring 예약 스케줄러 전체를 재시작하지 않는다.
대상 점검은 대역이고, 전달 포트는 시험 전용 JDK HTTP 통신을 사용한다. 페이로드는
값 비교를 위한 레코드 문자열이므로 운영 JSON 직렬화·Bearer 인증·공개 HTTPS·DNS
고정·SSRF 정책·HTTP 제한의 검증 증거가 아니다. 운영 아웃바운드 어댑터와 안전
설정에는 테스트용 우회 분기를 추가하지 않는다.

수신 측은 BATON의 내구성 중복 제거 구현을 대신하지 않는다. 이 시험이 증명하는
것은 WATCH의 프로세스 중단 후 리스 회수와 동일 이벤트 재전달이다. 실제 BATON의
중복 제거·효과 적용, 운영 Hikari 풀, 호스트 중단과 운영 처리량은 별도 검증이
필요하다. [부하 시험](load-recovery-test.md)과
[공개 전달 검증](public-staging-event-delivery.md)의 범위를 함께 참고한다.
